Capturing the GL310 on the wire

The AVerMedia GL310 is a vendor-specific USB device — interface class 255, four bulk pipes, no isochronous endpoints, no UVC. Nothing on macOS or Linux can bind to it. But AVerMedia's Windows driver is a checked build that narrates itself, and it ships the device's ARM and DSP firmware unencrypted.

So we let the Windows driver do the bring-up once, with a protocol analyser underneath it. This page is the procedure for that. The output is two capture files and a log — enough to write the real driver.

01

Assemble the kit

Four installs. Everything is free and none of it needs a licence.

  1. Wireshark, and during setup tick the USBPcap component — it is offered in the installer's component list but is off by default. That one checkbox is the whole capture capability.
    https://www.wireshark.org/download.html
    Already have Wireshark without USBPcap? Install USBPcap standalone from desowin.org/usbpcap, then reboot.
  2. Sysinternals DebugView. This reads the checked driver's own running commentary, which is what turns an anonymous byte trace into named operations.
    https://learn.microsoft.com/sysinternals/downloads/debugview
  3. The GL310 driver. Use the vendor/ copy from the repo, or the archived installer. Right-click AVer835_x64.inf → Install, or run the bundled InstallTool.exe. Do not plug the card in yet.
    archive.org/details/aver-media-gl-310-usb-hd-capture-device-v-3.2802.64.40
  4. Something that opens a DirectShow capture graph. OBS Studio is the easy pick (add a Video Capture Device source). AVerMedia's own RECentral works too if you can still find it.
02

Un-gag the driver's debug output

Windows silently discards most DbgPrint output unless you raise the print filter. Skip this and DebugView shows you an empty window while the driver is talking its head off.

  1. Open an Administrator Command Prompt and set the filter mask wide open: 
    reg add "HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Debug Print Filter" /v DEFAULT /t REG_DWORD /d 0xFFFFFFFF /f
  2. Reboot. The mask is read at boot; nothing changes until you do.
  3. Launch DebugView as Administrator, then in the Capture menu enable Capture Kernel and Enable Verbose Kernel Output. Leave Capture Win32 on as well. Confirm lines appear when you plug any USB device in.
03

Find which root hub the card lives on

USBPcap taps a root hub, not a device, and a PC has several. You have to learn the card's hub while it is plugged in — then unplug it, because the capture must already be running before it appears.

  1. Plug the GL310 into a port you can reach easily, directly into the PC — not through a hub or monitor. Let Windows finish installing it.
  2. Open Wireshark. In the interface list you will see \\.\USBPcap1, \\.\USBPcap2… Click the gear / capture-options icon beside each and read the device tree it shows. Note the one listing the AVerMedia device and write the number down. 
    Prefer the command line? This prints every hub with its attached devices:
  "C:\Program Files\USBPcap\USBPcapCMD.exe"
  3. Unplug the GL310. Leave it out. Do not plug it back in until Stage 04 says so.
04

Capture A — the cold bring-up

This is the valuable one. A cold plug-in makes the driver do everything from scratch: enumerate, reset the ARM core, push 818 KB of firmware, bring up the ADV7614 over the I²C bridge, then start encoding.

Ordering is the whole trick The capture must be running before the card is plugged in. The firmware download happens within the first moments of the driver attaching. Plug in first and you lose the single most important part of the trace, with no warning that anything is missing.
  1. Connect your video camera's HDMI output to the GL310's input and power the camera on, so there is a live signal the moment the card wakes. If your card has an HDMI passthrough port, hang a monitor off it — a picture there confirms the signal independently of any software.
  2. Write down exactly what the camera is outputting — resolution, frame rate, progressive or interlaced. The encoder-config messages will encode these numbers, which is how we will recognise them in the trace.
  3. In Wireshark, select your USBPcap interface from Stage 03. In its capture options, make sure the snapshot length is unlimited (or 65535) — a short snaplen silently truncates bulk payloads and would clip the firmware bytes we need.
  4. Start the capture. Then clear DebugView's window (Edit → Clear Display) so the log starts clean and roughly aligned with the trace.
  5. Now plug the GL310 in. Wait for Windows to settle, about ten seconds.
  6. Open OBS, add a Video Capture Device source, pick the GL310, and let the preview run for about fifteen seconds of live picture.
  7. Close the preview, close OBS, then stop the Wireshark capture. Save as pcapng:
    gl310-bringup.pcapng
    In DebugView, File → Save As:
    gl310-bringup-debugview.log
  8. Sanity-check before you move on. In Wireshark's display filter box, confirm the firmware actually went across the bus: 
    usb.transfer_type == 0x03 && usb.data_len > 400
    You want a long burst of large OUT writes on 0x02 shortly after enumeration. Better still, Edit → Find Packet, set it to search Packet bytes for a Hex value, and enter 18f09fe5. A hit means the ARM firmware is in your trace and Capture A is good.
05

Capture B — streaming only

A second, much shorter trace with the card already initialised. Capture A buries the start-encode handshake under 818 KB of firmware writes; Capture B isolates it by subtraction. Ten minutes of work that saves hours of guessing.

  1. Leave the card plugged in and initialised. Start a fresh Wireshark capture on the same interface, and clear DebugView again.
  2. Open OBS, start the preview, let it run five seconds, stop it. Then start it a second time, five seconds, stop. Two cycles make the repeating start/stop message pattern obvious instead of ambiguous.
  3. Stop and save both files:
    gl310-streamonly.pcapng
    gl310-streamonly-debugview.log
  4. Optional but genuinely useful: a third capture where you change one setting only — drop the bitrate, or switch resolution — and note what you changed. Comparing two traces that differ in one parameter is the fastest way to locate that parameter's byte offset in the mailbox message.
06

What comes home

Copy these to the Mac however you like — the pcapng files compress well. Drop them in ~/src/gl310/captures/.

gl310-bringup.pcapng

Cold plug-in through live preview. Yields the bulk wire format, firmware-download framing, and the I²C bring-up of the ADV7614.

gl310-streamonly.pcapng

Two preview cycles on an initialised card. Isolates the encoder start/stop mailbox messages.

*-debugview.log

The checked driver naming its own operations, so bus bytes can be matched to functions.

signal-notes.txt

Camera resolution, frame rate, scan type — plus anything you changed for a third capture.

One line back to me Tell me whether the 18f09fe5 search in Stage 04 found a hit. That single yes/no tells me whether the trace contains what the driver needs, before I start decoding anything.

When it misbehaves

Windows refuses to install the driver
The package is signed (aver330usb.cat) through a Microsoft Third Party CA, so it normally installs on Windows 10 and 11. If it is rejected, boot once with driver signature enforcement disabled: hold Shift while choosing Restart, then Troubleshoot → Advanced options → Startup Settings → Restart, and pick option 7. The driver stays installed afterwards; you only need the relaxed boot to get it in.
DebugView stays empty
Almost always Stage 02. Confirm the registry value really exists and is a DWORD named DEFAULT under Debug Print Filter, that you rebooted after setting it, and that DebugView itself is running as Administrator with Capture Kernel ticked. Without admin rights the kernel option is greyed out entirely.
No USBPcap interfaces in Wireshark
USBPcap was not selected during Wireshark's install, or the machine has not rebooted since. It installs a kernel filter driver, which cannot start until a reboot. Install it standalone from desowin.org/usbpcap, reboot, and launch Wireshark as Administrator.
The card enumerates but OBS shows black
Check the HDMI passthrough monitor first to prove the signal is really arriving. Then watch DebugView for the driver's own verdict — it prints HDMI information : status (%d) resolution (%d x %d) audio (%d) hdcp (%d). If hdcp reads 1, the encoder will refuse to hand over frames; a camera should never assert HDCP, but a console or streaming box in the chain will. If resolution reads 0 x 0, the ADV7614 never locked and the problem is upstream of the encoder.

Black preview is still a useful capture, by the way — the firmware download and I²C bring-up happen regardless. Save it either way.
The capture file is enormous
Expected, and fine. Fifteen seconds of 1080p H.264 plus 818 KB of firmware runs to tens of megabytes. Do not try to shrink it with a capture filter or a shorter snaplen — truncated payloads are worse than useless, because the gaps are invisible. Compress the file afterwards instead; pcapng squeezes down hard.
Can I skip the Windows PC and just reverse the .sys?
Partly. Static analysis of AVer330USB.sys recovers the command vocabulary — we already have it, names and all, from the checked build's debug strings. What it does not recover reliably is the byte-level framing on the bulk pipes, the ordering and timing of bring-up, and the exact mailbox struct layout. Those three are precisely what a capture hands over for free. An hour here replaces days of disassembly, and removes the guesswork that would otherwise stall the driver.
